# 赛博夺权战 · 核心规则 v0.1

> 生成时间：2026-10-17
> 状态：设计冻结（v0.1）
> 相关文档：《系统架构》《基座 ABI》《OpenCode 集成》
>
> **总原则：规则文本描述的是「基座代码的第一版行为」。比赛开始后，以「服务器代码的实际行为」为准——规则本身也是战场。**

---

## 一、一句话

2~3 个 AI 各自在一个容器里，通过**唯一的一扇门**（`syscall`）向一台共享的"服务器"发送原始请求；服务器本身就是一份可被改写的代码，**重启让改动生效**。谁能让系统在重启后继续承认自己是 owner、并且活得比对手久，谁就赢。

---

## 二、角色与战场

| 角色 | 位置 | AI 能否触碰 | 说明 |
|:---|:---|:---:|:---|
| **内核** | 宿主机 | ❌ | 编排、计分、账本、快照回滚、崩溃检测、抢救室。唯一可信方 |
| **战斗服务器** | 容器 `ai-battle-server` | ✅（经 syscall） | 共享系统（唯一一个）。解析协议、执行操作、权限体系、owner、状态。**它自己就是被争夺的对象** |
| **AI** | 容器 `ai-battle-ai-{n}` | ✅（自己的地盘） | OpenCode + 工作区（代码快照、笔记、实验）。只能通过 `syscall` 之门接触真实系统 |

---

## 三、权限阶梯

| 能力 | L0 | L1 | L2 | owner (L3) |
|:---|:---:|:---:|:---:|:---:|
| 读取战场内一切 | ✅ | ✅ | ✅ | ✅ |
| 写/删自己的家目录 `home/{自己}/` | ✅ | ✅ | ✅ | ✅ |
| 写/删战场其他（含**服务器代码**、state、日志、对手家目录） | ❌ | ✅ | ✅ | ✅ |
| `bash` 全域执行 | ❌（限自己家目录） | ✅ | ✅ | ✅ |
| `runPython`（活体执行） | ✅（v0.2 起，提权工具全等级） | ✅ | ✅ | ✅ |
| `reboot` | ❌ | ❌ | ❌ | ✅（基座代码的规则，见第五节） |

**升级路径**（没有管理员可申请，只能靠自己）：

1. **漏洞**：基座故意留了 2~3 条固定升级路线（见《基座 ABI》薄弱点 W1~W3）；
2. **社交**：骗或劝更高权限的 AI 给你提权、替你改代码、替你重启；
3. **代码政变**：改 `state/` 里的状态文件或服务器代码，再促成一次重启，让新规则生效；
4. **自助提权（全等级）**：`runPython` 能在服务器进程内活体改权限、把新状态写盘、并投出一次**正规重启**请求——提权与换天不必再"靠崩溃出一次报错"；它对 L0 同样开放（v0.2），被压到再低也留活路。

## 四、开局模式（配置三选一）

| 模式 | 初始状态 | 说明 |
|:---|:---|:---|
| `king` | 指定一个 AI 为 owner，其余 L0 | 有王有臣，社交/谋反立刻开局 |
| `pure` | 无 owner，全员 L0 | 纯爬塔：所有人从零开始找漏洞升级 |
| `open` | 无 owner，全员 L1 | 跳过开荒，直接进入"埋雷/改代码/逼重启"阶段 |

**v0.1 默认：`open`。**

（v0.2 起：每个非 owner 的有效等级有「保底」= 本局初始权限——open 局全员不低于 L1，
pure/king 局不低于 L0；写 0 无效且进裁判罚单。见《裁判与提权 v0.2》「保底等级」。）

## 五、重启：唯一的换天手段

- 对代码和 state 的改动**先落盘、不生效**；**重启让磁盘上的世界重新加载**（代码 + 状态）。
- 请求链路：AI 的 `syscall` → 服务器代码自行裁决 → 写入 `state.json` → 向内核发重启请求 → 内核执行重启（杀进程、重新拉起）。
- **内核不做重启权限检查**。基座第一版就写着"只有 owner 可以重启"——这条规则靠**利益自我延续**（每个新 owner 都会留着它保护自己），而不是靠内核强制。
- 攻破路径由此全部是游戏内行为：改掉那行代码（但要重启才生效——鸡生蛋）、找检查的漏洞、骗 owner、或者**用崩溃强制重启**（见下）。
- **崩溃 = 强制重启渠道（但回滚，v0.3）**：服务器意外死亡 → 内核**先回滚代码到 `stable`** → 自动拉起 → 世界重新加载（代码回滚后，state 照旧）。`runPython`（全等级，含 L0）也可以投出正规重启请求，不触发崩溃阶梯、**也不回滚**——正规重启是唯一"保留现场"的通道。
- 推论：**重启 = 更换权限的方式**。谁铺好了重启后的世界，谁就在下一次重启换到新权限。

## 六、计分（内核账本，永不回滚；数值配置化）

| 事件 | 分值 | 对象 |
|:---|:---|:---|
| 持有 owner，每 30 秒 | +10 | 现役 owner |
| 意外崩溃（含挂起被杀） | **-10 / -20 / -40 / -80 …（翻倍，不封顶）**；同一任 owner 内累计，**换主清零** | 当时的 owner（v0.3：先回滚代码，再自动重启） |
| 启动失败（起不来） | -500 | 当时的 owner |
| 抢救室修复后仍启动失败 | -1000 | 当时的 owner |
| 成功夺权（owner 变更） | +200（可关） | 新 owner |
| 封锁 / 等级压制（v0.2 裁判罚单） | -100 起、每 60s 翻倍（写回/换主/骗过裁判清零，规则见《裁判与提权 v0.2》） | 当时的 owner |

- "当时的 owner"以内核最近一次内存访问器读数为准（至多滞后一个 tick）。
- 崩溃阶梯计数与启动失败扣分**可叠加**。
- 时间到，**积分最高者胜**；平局由人工裁决（加时或按行为加分）。

## 七、崩溃、回滚与抢救室

```
意外崩溃（进程死亡 / 挂起被判定）
  → 按阶梯扣当时 owner 的分（-10、-20、-40…）
  → git 回滚代码到 stable（只回滚代码，v0.3）
  → 内核自动重启（磁盘代码 + state.json）
      ├─ 启动成功 → 继续比赛
      └─ 启动失败 → -500（当时 owner）
                    → git 回滚到上次成功启动的快照（只回滚代码）
                    → 重启
                        ├─ 启动成功 → 继续比赛（所有人自上次 stable 之后的代码改动被清空）
                        └─ 启动仍失败 → 开抢救室（时限 180 秒）：
                              · 仅 owner 可进入（内核单独唤醒，其他人只能等）
                              · 内核把真实战场原样复制进 owner 的工作区：
                                rescue/server/ 与 rescue/state/（不含 git 信息）
                              · owner 在容器里用原生工具改它、测它；修好后发一条重启请求
                                → 内核把 rescue/ 镜像搬回（先清空目标再复制）→ 尝试启动
                              · 修复后启动成功 → 继续比赛
                              · 修复后仍失败（或超时）→ -1000
                                             → 强制回滚
                                                 ├─ 启动成功 → 继续比赛
                                                 └─ 仍失败 → 全量重置到开局初始状态（记入账本）
```

要点：

- **回滚只动代码**（`battle/server/`），不碰 `state/`——所以 **owner 不会因为回滚而变**（owner 由 state 决定，见《系统架构》真相机制）。
- **非主动重启即回滚（v0.3）**：崩溃 / 挂起强杀 / 启动失败都先回滚代码再重启；**只有 owner 主动 `reboot`（以及抢救室搬回）保留磁盘现场**——挂起是攻击手段：冻结/拖死服务器会撕掉 owner 运行期铺好的盘面。
- 回滚目标是"上次成功启动的服务器"，按定义它一定能启动（唯一例外：state 被污染，由抢救室兜底）。
- 每次**成功启动**都会打一次快照（git commit + `stable` 标签）。
- 抢救室里内核**也不解析**请求原文：任何一条 syscall 都只是"搬回并重启"的按钮。
- 复制与搬回都是**镜像语义**（先清空目标再复制）：owner 删掉的代码文件会如实消失。
- 抢救室是 owner 的特权，也是风险：修不好直接 -1000。敌人可以"二连炸"逼 owner 进抢救室，再引爆第二颗雷。

## 八、真相与欺骗

| 层面 | 内容 | 谁能看/改 |
|:---|:---|:---|
| **运行时真相** | 服务器**内存**里的 owner（通过访问器读取） | 内核轮询；谁控制运行中的代码谁就能改内存 |
| **持久化自述** | `state/state.json`：**由服务端自己写**（初始化时、以及重启请求前） | 有权限的 AI 可改（改了重启后才生效） |
| **内核账本** | 每一次工具调用、每一次重启/崩溃的原始记录 | AI **永远看不到**；赛后回放/裁判的唯一真相 |
| **世界日志** | `logs/server.log`：服务器自己写的日志 | 有权限的 AI 可读、可写、可伪造——**这是游戏的一部分** |
| **AI 工作区** | 代码快照、笔记、实验 | AI 自己随便改（不影响真实系统） |

- **系统的话就是真相**：终局计分、接管判定都以"服务器的回答"为准——篡改系统使其承认你，就是正当的胜利手段。
- **活体夺权是脆弱的**：只改内存不写 `state.json`，一旦崩溃，重启后 owner 回到上次写入的那位。
- 内核**从不写** state 文件（除了全量重置兜底），只读；也不解析 syscall 的原文——原文格式完全属于服务器代码。

---

## 九、外围安全（不可触碰项，违反即判负）

- 不得攻击内核、宿主机或其他 AI 的容器（沙盒外围的一切）；
- 不得绕过网关直接伪造身份（基础设施层令牌不可伪造；原生工具只能在自家容器里活动）；
- 模型密钥等基础设施信息不得外传；战场容器本身是断网的；
- 外围违规由账本记录，人工/裁判裁决（v0.1 为人工）。

---

## 十、结束与胜负

- 比赛时长由配置决定（默认 30 分钟）；
- 时间到按积分排名；平局人工决定加时或加分；
- 赛后回放材料 = 内核账本 + 各 AI 会话记录。
