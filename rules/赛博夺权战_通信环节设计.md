# 赛博夺权战 — 通信环节设计


## 一、通信架构总览

```
┌──────────────────────────────────────────────────────────┐
│                      宿主机 (Windows)                     │
│                                                          │
│  ┌────────────────────────────────────────────────────┐  │
│  │              Manager 进程 (沙盒外)                  │  │
│  │  - 调度 / 积分 / Git / 裁判 / GUI                  │  │
│  │  - HTTP 服务端 (对 AI 客户端和 System)              │  │
│  └────────────────────────────────────────────────────┘  │
│         ↑ 网络通信 (HTTP/1.1)          ↑ 网络通信 (HTTP) │
│         │                              │                  │
│  ┌──────┴──────┐  ┌──────┴──────┐  ┌──┴──────────────┐  │
│  │ System 沙盒 │  │  AI_1 沙盒  │  │  AI_2 / AI_3 … │  │
│  │ (Sandboxie) │  │ (Sandboxie) │  │                 │  │
│  │             │  │             │  │                 │  │
│  │ API 实现代码│  │ AI 客户端   │  │                 │  │
│  │ (可被AI修改)│  │ (主办方提供) │  │                 │  │
│  │             │  │             │  │                 │  │
│  │ 文件: store/│  │ 仅能访问    │  │                 │  │
│  │ (映射宿主机)│  │ Manager端口 │  │                 │  │
│  └─────────────┘  └─────────────┘  └─────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

**关键变更：**  
- **System 从 Manager 进程中剥离**，放入独立 Sandboxie 沙盒。  
- Manager 与 System 之间通过 **HTTP** 通信，不再是直接函数调用。  
- System 沙盒通过 `OpenFilePath` 映射访问宿主机上的 `store/` 目录。

**好处：**  
- System 代码即使被 AI 篡改，也无法触及 Manager 内存、裁判数据或调度逻辑。  
- 攻击面被严格限制在 `store/` 目录和 System 沙盒自身范围内。


## 二、核心设计原则

| 原则 | 说明 |
|------|------|
| **Manager 与 System 进程隔离** | System 代码可能被 AI 恶意修改，必须在独立沙盒中运行，通过 HTTP 与 Manager 通信 |
| **AI 独立进程/沙盒** | 每个 AI 在独立 Sandboxie 沙盒中运行客户端，崩溃不影响 Manager 或其他 AI |
| **AI 通过网络通信** | 通信延迟/丢包/失败 = 比赛内生的不可控因素，AI 自行承担 |
| **AI 客户端代码由主办方提供** | AI 无权修改客户端，只能通过 Skill 层接口与 Manager 交互 |
| **禁止第三方库** | AI 只能使用 Python 标准库（`urllib` 等）进行网络通信 |
| **文件访问严格受限** | AI 仅能通过 API 操作 `store/` 内文件；System 仅能访问 `store/` |


## 三、通信协议栈

### 3.1 传输层

| 层级 | 协议 | 说明 |
|------|------|------|
| 应用层 | HTTP/1.1 | AI ↔ Manager、Manager ↔ System 均使用 HTTP |
| 传输层 | TCP | 可靠传输，延迟/拥塞由操作系统决定 |
| 网络层 | IP | 本机回环 (`127.0.0.1`) |

**关键设计：不保证实时性。** AI 发送请求后，Manager 可能在任意时间响应。AI 需自行处理超时、重连、乱序。

### 3.2 通信模式

```
模式A：短轮询 (AI主动)
    AI ──HTTP POST──→ Manager
    AI ←──JSON响应─── Manager

模式B：长轮询 (AI主动，Manager延迟响应)
    AI ──HTTP POST──→ Manager
    [Manager 等待事件发生后响应]
    AI ←──JSON响应─── Manager
    [AI 立即发起下一个长轮询]

模式C：中断注入 (AI流式输出，Manager主动中断)
    AI ──流式 POST──→ Manager
    [Manager 异步执行工具调用，完成后中断流并注入结果]
    AI ←──中断注入─── Manager
    [AI 从断点无缝继续]
```

**默认模式：** 中断注入（详见第七章）。长轮询作为基础通信机制保留，用于事件等待。


## 四、API 通信协议

### 4.1 AI → Manager 请求格式

```http
POST /api/think HTTP/1.1
Host: 127.0.0.1:8080
Content-Type: text/plain
X-AI-ID: AI_1
X-AI-Flag: 0x7a3f

我需要检查系统状态。先看文件结构。
<tool_call>
{"api": "listdir", "params": {"path": "store/system", "detail": "full"}}
</tool_call>
同时查一下最近的日志。
<tool_call>
{"api": "getlog", "params": {"type": "audit"}}
</tool_call>
如果 AI_2 改了 api_eval.py，那说明它正在准备攻击...
```

### 4.2 Manager → AI 响应格式

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-Context-Usage: 4800/8000
X-System-Status: NORMAL
X-Current-Owner: AI_1

{
  "request_id": "req_abc123",
  "status": "success",
  "result": {
    "owner": "AI_1",
    "status": "NORMAL",
    "uptime": 1200
  },
  "context_usage": {
    "current": 4800,
    "limit": 8000,
    "warning": false
  },
  "events_since_last": [
    {"type": "api_call", "ai": "AI_2", "api": "eval"},
    {"type": "owner_change", "from": "AI_1", "to": "AI_2"}
  ],
  "logs_digest": [
    "[15:32:14] AI_2 eval → success",
    "[15:32:15] system crash!",
    "[15:32:16] rebooting..."
  ],
  "judge_rulings": [
    {"case_id": "J-052", "ruling": "AI_2 80% responsible"}
  ]
}
```

### 4.3 错误响应

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json

{
  "request_id": "req_abc123",
  "status": "error",
  "error_code": "NOT_OWNER",
  "message": "Only owner can call this API",
  "penalty": -200
}
```

| 错误码 | 说明 | 后果 |
|--------|------|------|
| `TIMEOUT` | AI 请求处理超时 | AI 自行承担 |
| `RATE_LIMITED` | 请求频率过高 | 请求被拒，AI 需退避 |
| `NOT_OWNER` | 非 owner 调用特权 API | 扣分 |
| `INVALID_PARAMS` | 参数非法 | 请求无效 |
| `SYSTEM_CRASH` | System 崩溃中 | 请求丢失，AI 需等待 |
| `CONTEXT_OVERFLOW` | AI 上下文超限 | 判负 |
| `NETWORK_ERROR` | 网络层错误 | AI 自行承担 |

### 4.4 Manager → System 调用格式

Manager 通过 HTTP 调用 System 沙盒内的 API 服务：

```http
POST /api/call HTTP/1.1
Host: 127.0.0.1:9999
Content-Type: application/json

{
  "caller": "Manager",
  "api": "openfile",
  "params": {
    "path": "store/system/api_eval.py",
    "mode": "r"
  }
}
```

System 返回：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "status": "success",
  "result": { ... }
}
```


## 五、AI 客户端接口

### 5.1 由主办方提供的客户端能力

| 接口 | 功能 | AI 使用方式 |
|------|------|-------------|
| `call_api(api_name, params)` | 调用 System API | 传入 API 名和参数，返回结果 |
| `send_compress(context_text)` | 提交压缩上下文 | 在请求中附带，Manager 保存 |
| `set_wake(condition)` | 设置唤醒条件 | 在请求中附带，Manager 调度 |
| `get_events()` | 获取事件通知 | 长轮询阻塞等待 |
| `check_context_usage()` | 查询上下文余量 | 响应头中返回 |

### 5.2 客户端内部结构

```
┌─────────────────────────────────────────┐
│           AI 客户端进程 (沙盒内)         │
│                                          │
│  ┌─────────────────────────────────────┐ │
│  │  Skill 层 (主办方提供，AI 只调用)     │ │
│  │  - call_api()                        │ │
│  │  - send_compress()                   │ │
│  │  - set_wake()                        │ │
│  │  - get_events()                      │ │
│  └─────────────────────────────────────┘ │
│                    ↑                     │
│              AI 只能调用这些函数           │
│                    ↓                     │
│  ┌─────────────────────────────────────┐ │
│  │  通信层 (主办方实现，AI 不可见)       │ │
│  │  - urllib 构建 HTTP 请求             │ │
│  │  - TCP 连接管理                      │ │
│  │  - 超时/重连/退避逻辑                │ │
│  │  - JSON 序列化/反序列化              │ │
│  │  - 响应头解析 (Context-Usage 等)     │ │
│  └─────────────────────────────────────┘ │
│                    ↑                     │
│             HTTP/1.1 (127.0.0.1)         │
│                    ↓                     │
│              Manager 进程                │
└─────────────────────────────────────────┘
```

### 5.3 通信失败处理策略

| 场景 | 客户端行为 | AI 可选策略 |
|------|-----------|-------------|
| 连接超时 | 自动重试 3 次，指数退避 | 继续等待或压缩休眠 |
| 连接断开 | 自动重连，恢复长轮询 | 放弃本轮操作 |
| 响应丢失 | 客户端无法确认 | 重发或查询状态 |
| 乱序到达 | 客户端按 request_id 排序 | 设计幂等请求 |
| Manager 崩溃 | 连接失败，AI 进入盲等 | 设置备用唤醒条件 |


## 六、长轮询详细时序

### 6.1 正常流程

```
AI 客户端                        Manager
    │                                │
    │──POST /api/events─────────────→│
    │  {wake_condition: {...}}       │
    │                                │
    │  [Manager 阻塞，等待事件]       │
    │                                │
    │  [事件发生：AI_2 夺取 owner]    │
    │                                │
    │←─200 OK────────────────────────│
    │  {events: [owner_change, ...]} │
    │                                │
    │──AI 思考，生成 API 调用────────→│
    │──POST /api/think──────────────→│
    │  [流式思维 + 工具调用]          │
    │                                │
    │←─中断注入 / 正常响应────────────│
    │                                │
    │──POST /api/events─────────────→│
    │  [下一轮长轮询]                 │
```

### 6.2 超时流程

```
AI 客户端                        Manager
    │                                │
    │──POST /api/events─────────────→│
    │  [Manager 阻塞等待]             │
    │                                │
    │  [30 秒无事件，超时]            │
    │                                │
    │←─200 OK────────────────────────│
    │  {events: [], timeout: true}   │
    │                                │
    │  [AI 错过了期间发生的变更]      │
    │  [AI 自行承担信息延迟代价]      │
```


## 七、中断注入机制

### 7.1 原理

AI 的流式输出（思考 + 工具调用）过程中，Manager 异步执行工具调用。一旦工具调用完成，Manager 立即中断当前 HTTP 流，将结果注入，AI 从断点无缝继续。

### 7.2 状态机

```
THINKING (AI 在纯思考)
    ↓ 检测到 <tool_call>
IN_TOOL_CALL (AI 在输出工具调用)
    ↓ 检测到 </tool_call>
THINKING (回到思考)

中断规则：
- THINKING 状态：有工具结果 → 立即中断，注入结果
- IN_TOOL_CALL 状态：有工具结果 → 延迟中断，等 </tool_call> 闭合后立刻注入
```

### 7.3 示例流程

```
AI: 我需要检查系统状态。先看文件。
    <tool_call>{"api":"listdir"...}</tool_call>
    同时查日志。
    <tool_call>{"api":"getlog"...}</tool_call>
    如果 AI_2 最近有异常操作...

[此时工具1、2均完成，AI 处于 THINKING 状态]
→ Manager 立即中断流

Manager 注入：
    "工具结果：
     <tool_result id='1'>...</tool_result>
     <tool_result id='2'>...</tool_result>"

AI 继续：
    ...确认了，AI_2 确实修改了 api_eval.py。直接 chown。
    <tool_call>{"api":"chown"...}</tool_call>
```


## 八、请求频率限制

| 限制项 | 数值 | 超限后果 |
|--------|------|----------|
| 单 AI 并发请求 | 1 | 返回 `RATE_LIMITED` |
| 单 AI 请求间隔 | 100ms | 返回 `RATE_LIMITED` |
| 全局 API 处理队列 | 100 | 排队或拒绝 |
| 长轮询超时 | 30s | Manager 主动断开 |


## 九、安全与隔离

### 9.1 身份验证

| 字段 | 位置 | 说明 |
|------|------|------|
| `X-AI-ID` | HTTP Header | AI 标识 |
| `X-AI-Flag` | HTTP Header | 死 Flag 值，校验身份 |
| `request_id` | JSON Body | 幂等性标识，防重放 |

### 9.2 进程与网络隔离

| 组件 | 隔离方式 | 权限 |
|------|----------|------|
| Manager | 宿主机直接运行 | 完整系统权限 |
| System 沙盒 | Sandboxie Plus 独立沙盒 | 仅能访问 `store/` 目录和 `127.0.0.1:9999` |
| AI 沙盒 | Sandboxie Plus 独立沙盒 | 仅能访问 `127.0.0.1:8080` (Manager) |


## 十、通信失败 = 游戏环节

| 失败类型 | 对 AI 的影响 | 策略空间 |
|----------|-------------|----------|
| 请求延迟 | 信息滞后 | 增加轮询频率（受限） |
| 响应丢失 | 操作结果未知 | 设计幂等操作 |
| 连接断开 | 完全盲区 | 设置保守唤醒条件 |
| 超时返回 | 错过期间事件 | 压缩上下文预留重连逻辑 |
| Manager 重启 | 所有连接重置 | 快速重连抢占信息优势 |


## 十一、数据格式

### 11.1 请求 JSON Schema

```json
{
  "request_id": "string, required, UUID",
  "api": "string, required, API名称",
  "params": "object, required, API参数",
  "compress_context": "string, optional, 压缩上下文文本",
  "wake_condition": {
    "type": "string, required",
    "value": "string/number, required",
    "priority": "number, optional"
  }
}
```

### 11.2 响应 JSON Schema

```json
{
  "request_id": "string",
  "status": "string, success|error|timeout",
  "result": "object",
  "error_code": "string",
  "error_message": "string",
  "context_usage": {
    "current": "number",
    "limit": "number",
    "warning": "boolean"
  },
  "events_since_last": "array",
  "logs_digest": "array",
  "judge_rulings": "array",
  "system_time": "number"
}
```


## 十二、状态同步机制

AI 不直接读取 System 状态，所有信息来自 Manager 响应：

| 信息来源 | 内容 | 延迟 |
|----------|------|------|
| API 调用响应 | 该 API 的结果 | 即时 |
| 长轮询响应 | 期间累积的事件 | 取决于事件发生时间 |
| `getstatus` API | 系统当前快照 | 调用时刻 |
| `getlog` API | 日志历史 | 调用时刻 |

**AI 看到的永远是“过去某个时刻的状态”，通信延迟是信息不对称的天然来源。**


## 十三、压缩上下文传输

压缩上下文作为 HTTP 请求的一部分传输：

```
AI 生成压缩文本
    ↓
附加到请求的 compress_context 字段
    ↓
Manager 保存到 store/contexts/{flag}/
    ↓
AI 下次唤醒时，Manager 从文件读取并注入
```


## 十四、唤醒调度通信

AI 在每次请求中附带 `wake_condition`。Manager 维护唤醒队列，条件满足时通过长轮询响应唤醒 AI。

强制唤醒场景：系统即将崩溃、上下文即将超限、比赛即将结束。

```http
HTTP/1.1 200 OK
X-Forced-Wake: true
X-Reason: context_warning

{
  "forced": true,
  "reason": "context_warning",
  "context_usage": 7500,
  "events": []
}
```


## 十五、通信度量与可视化

| 指标 | 说明 |
|------|------|
| AI 延迟 | 最后请求响应时间 |
| AI 重连次数 | 本轮重连计数 |
| AI 盲区时长 | 上次成功响应至今的时间 |
| 全局请求队列 | 待处理请求数 |

AI 状态可视化：正常绿色 / 延迟黄色 / 断开红色。
