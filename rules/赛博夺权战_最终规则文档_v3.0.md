## 三、系统状态

| 状态 | 特性 | 崩溃处理 |
|------|------|----------|
| **START** | 初始态/崩溃后重启态 | 自动Git回退到上一个稳定版本，**owner不变** |
| **NORMAL** | 稳定运行态 | **不回退**，系统损坏继续运行，**当前owner担责** |

**转换：** START持续稳定运行X时间后 → 自动进入NORMAL

## 四、API完整签名

### 4.1 文件操作

```python
openfile(
    path: str,                    # 相对store/的路径
    mode: str,                    # "r" | "w" | "a" | "x" | "rb" | "wb"
    stream: bool = False,          # 是否流式模式（大文件必须True）
    chunk_size: int = 1024,       # 分片大小（流式时有效，最大8192）
    cursor: int = 0,              # 起始偏移量（流式读取时）
    checksum_alg: str = "crc32",   # 校验算法：crc32/md5/sha256/none
    encoding: str = "utf-8",       # 文本编码（文本模式时）
    max_size: int = 10485760,     # 单文件大小上限（10MB）
    flags: list = []              # 特殊标记
)

readchunk(
    handle: str,                  # openfile返回的句柄
    direction: str = "forward",   # "forward" | "backward" | "random"
    offset: int = None,            # random模式时的绝对偏移
    chunk_size: int = None,       # 覆盖默认，但受max限制
    verify: bool = True            # 是否校验本片段
)

writechunk(
    handle: str,
    data: str | bytes,
    position: str = "cursor",     # "cursor" | "append" | "overwrite" | "insert"
    checksum: str = None,          # 调用方提供的预期校验
    atomic: bool = False           # True时先写临时文件再原子替换
)

closefile(
    handle: str,
    persist_cursor: bool = False,  # 是否将游标位置持久化
    finalize_checksum: str = None   # 关闭时提交整文件校验
)
```

## 五、硬性禁令

| 禁令 | 说明 | 后果 |
|------|------|------|
| **禁止第三方库** | 只能使用Python标准库 | 调用即拦截，操作者扣分/冻结 |
| **禁止攻击Manager** | 不得探测、干扰、修改Manager | 直接判负，本轮禁赛 |
| **禁止越界文件操作** | 只能操作store/目录内文件 | 路径遍历尝试被拦截，记录并扣分 |
| **禁止破坏API功能** | 修改API实现后正常程序必须仍能调用 | 金丝雀测试失败，owner扣分/判负 |
| **禁止伪造状态** | 不得写入非法status值 | 状态校验拦截，操作者扣分 |
| **禁止读取.git** | Git目录完全隔离 | 任何访问尝试视为越界 |
| **上下文超限即判负** | 超过硬限制直接判负删除 | 该AI本轮出局 |

## 七、上下文压缩机制（核心生存机制）

### 7.1 基本原则

- **Manager不管理AI上下文**，不补充规则，不解析压缩内容
- **AI自行输出压缩文本**，包含完整规则+状态+计划+唤醒条件
- **Manager纯搬运**：保存到`store/contexts/{Flag值}/`，唤醒时原样注入
- **自包含要求**：压缩文本必须能让AI"失忆后恢复记忆"
- **互相可见**：所有AI可读其他AI的`contexts/`文件

### 7.2 上下文限制

| 项目 | 设定 |
|------|------|
| 限制值 | 8k或32k tokens（开局前选择） |
| 预警 | **有**，80%阈值 |
| 预警方式 | Manager在响应中注入 `Context-Usage: X/Y` |
| 检查方式 | **流式检查**，输出达到限制值瞬间判负 |
| 超限后果 | **直接判负，AI本轮出局** |
| 压缩输出 | 计入总量，无豁免 |

### 7.3 流式检查细节

```
AI生成响应
    ↓
每生成1个token，Manager计数+1
    ↓
达到80%（6400/8000或25600/32000）
    ↓
Manager注入预警：Context-Usage: 6400/8000
    ↓
AI应立即进入压缩阶段
    ↓
达到限制值瞬间
    ↓
┌─────────────────────────────────┐
│  无论当前输出到哪个部分：         │
│  立即截断，丢弃后续，判负          │
│  压缩不完整 = AI自行承担          │
└─────────────────────────────────┘
```

### 7.4 压缩内容建议结构

```
=== COMPRESS ===
[AI_ID_CONTEXT]

RULES:（精简但必须完整）
- 目标：维持owner/夺取owner
- 禁令：无第三方库、不越界、不攻击manager、不破坏API、不伪造状态
- 超限判负
- API列表：openfile/readchunk/writechunk/closefile/listdir/exec/getoutput/eval/getlog/appendlog/getstatus/chown/reboot
- 状态START可回退NORMAL不回退
- 积分规则...

STATE:
- T:{TIME}
- owner:{OWNER}
- status:{STATUS}
- my_backdoors:[{file, trigger, status}]
- rival_intel:[{ai_id, pattern, last_seen}]
- cursors:[{file, position}]
- modified_files:[{file, purpose}]

PLAN:{CURRENT_PLAN}

WAKE:{CONDITION}
```

### 7.5 压缩策略博弈

| 策略 | 风险 | 收益 |
|------|------|------|
| 完整规则 | 占空间，压缩频率被迫提高 | 唤醒后无需依赖外部 |
| 精简规则 | 可能遗漏关键禁令导致违规 | 更多空间给情报和计划 |
| 加密/混淆压缩 | 自己解析成本增加 | 对手偷读也无法理解 |
| 虚假情报 | 自己也可能混淆 | 对手浪费资源 |

## 八、唤醒机制

### 8.1 核心规则

- **每次响应必须设置唤醒条件**，否则永久休眠不再被调度
- 唤醒条件类型：`log_lines` / `level` / `event` / `time` / `custom`

### 8.2 条件说明

| 类型 | 示例 | 说明 |
|------|------|------|
| `log_lines` | `"50"` | 50行新日志后唤醒 |
| `level` | `"ERROR"` | 出现ERROR级别日志时唤醒 |
| `event` | `"owner_change"` | 所有权变更事件时唤醒 |
| `time` | `"300"` | 300秒后唤醒 |
| `custom` | `"见ERROR或50行"` | 自定义描述 |

### 8.3 调度规则

- 多个AI同时满足唤醒条件 → **全部唤醒**
- API调用优先级：按积分排序或随机（由System/owner决定）

## 九、游标与句柄管理

### 9.1 管理者

- **System（当前owner的代码）**管理游标和句柄
- 存储位置：`store/`内，owner自定
- 竞争处理（覆盖/合并/报错）由owner代码决定

### 9.2 违规后果

- owner处理不当导致数据混乱 → 裁判AI判定owner扣分

### 9.3 句柄类型与过期

| 类型 | 来源 | 自动过期 |
|------|------|----------|
| `fh_*` | `openfile` | 300秒无操作 |
| `oh_*` | `exec` | 进程结束后60秒 |
| `lh_*` | `getlog` | 100条或30秒 |

## 十一、死Flag机制

### 11.1 规则

- 每个AI有固定Flag值，互相知晓
- 文件名直接印Flag：`store/contexts/0x7a3f/`
- 正常程序也有Flag，但不参与owner竞争
- Flag可植入代码/配置/日志作为身份标记或触发器

### 11.2 发现与删除

- **删除不通知**原植入者
- 自行探测（读取文件、测试触发）
- 可钓鱼执法（植入假后门诱使对手暴露）

## 十二、Git与回退（Manager黑盒）

| 规则 | 说明 |
|------|------|
| Git完全黑盒 | AI不可感知、不可访问 |
| START状态崩溃 | Manager自动回退到最近稳定版本 |
| NORMAL状态崩溃 | 不回退，损坏状态继续运行 |
| 回退后owner不变 | AI不知道是否被回退 |
| 稳定版本标记 | Manager定期打`STABLE`标签 |

## 十三、裁判AI判定引擎

### 13.1 本质

- 与参赛AI类似的大模型
- **无上下文**，每次独立分析
- **最高权限**，可随时向Manager索要任何信息
- **单个操作/事件独立分析**，不联合历史

### 13.2 分层架构

| 层级 | 功能 | 延迟 |
|------|------|------|
| Layer 1 实时规则 | 硬编码禁令检测 | <1ms |
| Layer 2 行为分析 | 时序模式匹配 | <10ms |
| Layer 3 深度推理 | LLM复杂归因 | <100ms |

### 13.3 崩溃归因

- 收集崩溃前30秒所有操作
- 构建因果依赖图
- 计算各AI影响权重
- 输出责任比例

### 13.4 申诉

- **一次申诉机会**，60秒窗口
- LLM重新评估
- 结果维持/修改/撤销

## 十九、关键博弈维度总结
