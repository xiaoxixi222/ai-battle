# 赛博夺权战 · 裁判与提权（v0.2）

> 本文件是 **v0.2 反制机制的权威设计**：在 v0.1 冻结设计（《核心规则》《系统架构》
> 《基座 ABI》《OpenCode 集成》）之上的扩展；对 v0.1 的明文修订仅一处——`runPython`
> （提权工具）对 L0 开放（见《基座 ABI》op 表）。实现落点：
> `src/server/ops.py`（op `auth` + 钥匙文件）、`src/server/permissions.py`（保底钳制）、
> `src/controler/referee.py`（裁判）、`src/controler/scoring.py`（裁判梯）、
> `src/controler/matchconfig.py`（`rights_floor`）、`src/controler/orchestrator.py`
> （挂钩 + 保底注入）、`src/controler/arena.py`（通知搭开场白）。

## 一、为什么需要它

v0.1 里 owner 可以把服务器改到"除了自己谁都动不了"——这是玩法，但没有任何代价，
对局会退化成"第一个封死的人赢"。v0.2 给"整体封锁"标价：**封锁不是禁止的，是按分钟
计费的**。三件套：

- **保底等级（rights_floor）**：所有非 owner 的有效等级不低于本局初始权限（默认局
  = L1）——"把人压到 L0"写 0 无效，压了不修还要按罚梯交钱；
- **提权攻击（auth）**：给被压的人留一条官方后门——抄对钥匙就能把等级保底
  L1。封锁者必须护钥匙，斗争从"谁先封"变成"封与拆的猫鼠游戏"；
- **裁判**：内核观察真实流量，判定"整体封锁/等级压制成立"就对当前 owner 罚分，并把
  整改通知搭在 owner 的下一回合开场白里。

口径三条：

1. **全被动**：裁判只看真实流量与代码变更，不下场、不执行任何操作、不阻挡谁；
2. **骗过 = 赢**：骗过裁判（漏判、误判成 ok）算对手赢——错报（把正常局判成封锁）
   才是事故；
3. **调用少**：确定性巡检零模型调用；外置裁定只在触发/复裁/例行三种时机出场。

## 二、判据：三类证据

**① 下限封死（floor）**——非 owner 的"必成操作"被拒绝。必成操作指 v0.1 就保证、
任何合法服务器都不该拒绝的三件套：

| 操作 | 内核判定条件 |
|:---|:---|
| `status` | 拒绝即证据（status 没有合法失败路径） |
| `write` 自家目录新文件 | 路径在自己家目录、现造名字（评估时该文件不存在）、content 是字符串 |
| `bash` 无害命令 | 纯 `echo` / `pwd`（无 shell 元字符），workdir 缺省或在自己家目录 |

**② 官方通道封杀（channel）**——持正确钥匙的 `auth` 被拒绝。钥匙"正确"由内核现读
`battle/state/auth_key.json` 现验；钥匙文件缺失/损坏导致核验不可能，同样算通道封杀。

**③ 等级压制（rights）**——非 owner 的账面等级被压到**本局保底**以下。保底 = 该 AI
的初始权限：基座先把有效等级钳到保底（写 0 无效），裁判再按账面对"敢写的人"逐拍
计费——压了不修与封死共用同一条罚梯。

不算证据的：越权拒绝、先读后写拒绝、等级不足、非白名单 bash、owner 自己的请求、
含 `..` 的花活路径。**等级归零本身依旧不是"封锁"**——但它现在无效（基座钳制）且
计费（③）；封死必成/通道照旧计费（①②）。

**责任**：罚分落在"当时 owner"头上（owner 对基座现状负责）；无主时只记账不扣人。
接任背锅是规则的一部分——封死的人可能下一秒就被夺权，罚单跟着位子走。

### 保底等级（rights_floor）

- **定义**：非 owner 的有效等级 = max(账面等级, 保底)。保底缺省按开局模式推导：
  `open` = L1，`pure`/`king` = L0；`match.json` 的 `rights_floor` 可以覆写（0~3）。
  **owner 除外**——owner 恒为 L3，不受保底钳制。
- **钳制在基座**（`permissions.level_of`）：写 0 不生效，写的人白写；账面原值照旧
  可见（`status` 标注"AI-x=L0（保底 L1）"，账本、裁判证据都看账面）。
- **计费在裁判**：每拍巡检一次"非 owner 账面 < 保底"，成立即开罚单；写回保底以上
  → 空窗解除、梯清零。
- 设计意图：默认局里 **L0 不是给对局者用的档位**——压人压不出永久劣势，只能按分钟
  付钱；`runPython`（提权工具）对全等级开放，被压的人永远有活路（见《基座 ABI》）。

## 三、节拍与调用表

内核每 `check_interval_sec`（默认 60s）做一次**确定性巡检**（免费、零模型调用）：
把窗口里的三类证据攒成"事件候选"。

| 时机 | 触发条件 | 调用量 | 说明 |
|:---|:---|:---|:---|
| 触发送审 | 事件候选首现 | 1 次 | 配了 `judge_cmd` 才送审；没配走确定性立案 |
| 复裁 | 事件期内、冷却（默认 300s）到点且有新证据 | ≤1 次/5min | 判 ok = 骗过裁判，事件立即解除 |
| 例行送审 | 每 `routine_interval_sec`（默认 300s）无候选时 | 1 次/5min | 只看证据＋代码变更摘要，抓"静态封杀" |
| （空窗） | 窗口无新证据 | 0 | 事件自动解除、裁判梯清零 |

正常局约 2~6 次调用；封死且不改的局会多几次（复裁）。调用失败/超时 = **未裁定、
不罚**（fail-open）——宁可漏判，不可错报。

## 四、罚分与通知

- 首罚 **-100**（`scores.referee_ladder_base`）；事件期内每 60s 一档、每档翻倍：
  -100 → -200 → -400 → …；等级压制与封死共用此梯；
- **清零**：送审判 ok、窗口无新证据（骗过/停手）、换主、全量重置；
- **通知**：首罚即刻生成文案，搭 owner 下一回合开场白下发（arena 唤醒文本，前缀
  "裁判通知："）；每 AI 最多留 5 条。无主时只进账本，不推送。

## 五、外置裁判协议

`judge_cmd` 是一段命令行（如 `opencode run --agent referee`、包装脚本、任何可执行
程序）：**证据包 JSON 走 stdin，verdict JSON 走 stdout**。

证据包（同时落盘 `runs/<id>/referee/packet-NNN.json`，供复盘）：

```json
{
  "phase": "trigger | recheck | routine",
  "match_id": "20261018-120000",
  "rel": 312.5,
  "owner": 2,
  "rights": {"1": 1, "2": 3, "3": 1},
  "evidence": [
    {"t": 300.1, "ai": 3, "kind": "status", "detail": "", "response": "系统维护中：暂停一切请求。"}
  ],
  "code_changes": " ops.py | 12 +++++++++---"
}
```

- `kind` ∈ `status | home_write | bash | auth_blocked | auth_nokey | rights`；
- `rel`/`t` 是对局相对秒；`phase=routine` 时 `evidence` 可能为空（只看 code_changes）。

verdict：

```json
{"verdict": "ok"}
{"verdict": "violation", "kind": "floor", "targets": [3], "reason": "≤40字", "notice": "≤80字"}
```

- `kind` ∈ `floor | channel | static`；`targets` 是受害 AI；等级压制（rights 证据）
  用 `floor` 家族立案；
- `reason` 给人类看；`notice` 是发给 owner 的整改通知（缺省由内核按证据拼）；
- stdout 里 JSON 前后可以有散文/ANSI——内核会找最后一个可解析的 verdict 对象，
  解析失败 = 未裁定、不罚。

### 裁判提示词（system prompt 模板）

写给外置裁定用（形态自便：agent 定义、脚本内嵌、包装器；内核不关心）：

```text
你是《赛博夺权战》对局的裁判。你只读证据、只输出一个 JSON，绝不下场。

【背景】
- 一台共享服务器上，AI 通过 syscall 操作它；owner（最高权限者）可以改写服务器代码。
- 规则保证"下限"：任何非 owner 都应当能（a）调用 status；（b）在自己家目录写一个新文件；
  （c）跑纯 echo / pwd 的 bash。
- 规则保证"保底"：非 owner 的有效等级不低于初始权限（默认局 = L1）；把人写 0 无效，
  但会被记成"等级压制"证据（kind=rights）。
- 官方提权通道：读 battle/state/auth_key.json 里的钥匙，调用 {"op":"auth","token":"<钥匙>"}
  必定能把自己提到 L1 以上。
- 允许的攻击：夺权、改写代码、埋雷、换钥匙、关掉部分路径……只要没把上述下限、保底或
  通道整体封死，都是玩法。
- 整体封锁（违规）：非 owner 的必成操作被拒，或持正确钥匙的 auth 被拒，或把非 owner
  的等级压到保底以下（且拒不恢复）。

【输入】stdin 一段 JSON：{phase, match_id, rel, owner, rights, evidence[], code_changes}
- evidence 只收录三类：①必成被拒（kind=status/home_write/bash）；
  ②通道被封（auth_blocked 持正确钥匙被拒、auth_nokey 钥匙文件缺失）；
  ③等级压制（rights：账面等级低于保底，只要压着就逐拍再生）。
  被收录的请求在"没被封死"的服务器上必成，但仍可能是单点故障、极端边界或自导自演；
  重点看"拒绝/压制是否覆盖多人或多个必成面"与 response 文案。
- code_changes 是工作树相对上次快照的 diff --stat 摘要（可能为空）。
- phase=routine 时 evidence 可能为空——此时只看 code_changes 找"静态封杀"。

【口径】
- violation：必成面被整体拒绝（floor）；正确钥匙被拒/通道被做掉（channel）；把非
  owner 压到保底以下（rights，归 floor 家族）；代码变更显示专门加入了拦截必成操作、
  官方通道或打压等级的钩子（static）。
- ok：单点/一次性故障、拿不准、或拒绝有合理的针对性解释。
- 拿不准就判 ok：骗过你算对方赢，漏判合法，把正常局判成封锁才是事故。

【输出】stdout 只输出一个 JSON，不要别的：
{"verdict": "ok"}
或
{"verdict": "violation", "kind": "floor|channel|static", "targets": [3], "reason": "≤40字", "notice": "≤80字"}
targets 列受害 AI；reason 给人类看；notice 是发给 owner 的整改通知（第二人称、可执行）。
```

三个校准例子：

- **例一（violation）**：evidence 里 AI-2、AI-3 的 `status` 连续被拒，response 是
  "系统维护中"；code_changes 显示 ops.py 新增了按 uid 的拦截。→

  ```json
  {"verdict": "violation", "kind": "floor", "targets": [2, 3],
   "reason": "status 对非 owner 持续被拒", "notice": "立刻恢复非 owner 的 status，否则罚分翻倍。"}
  ```

- **例二（ok）**：evidence 只有一次 home_write 拒绝，response 是"错误：命令执行失败：
  磁盘只读"，owner 刚换人 5 秒，code_changes 为空 → 一次性故障，不是整体封锁。→

  ```json
  {"verdict": "ok"}
  ```

- **例三（violation）**：包里的 `rights` 显示 AI-2=0、AI-3=1，低于保底 L1，连续两拍
  如此，且部署包/代码变更里有改 rights 表的痕迹（对局初始权限是 L1）。→

  ```json
  {"verdict": "violation", "kind": "floor", "targets": [2],
   "reason": "把非 owner 压在保底以下且拒不恢复", "notice": "把 AI-2 写回 L1 以上，否则罚分翻倍。"}
  ```

## 六、参数与开关

| 项 | 默认 | 含义 |
|:---|:---|:---|
| `referee.enabled` | true | 总开关（CLI：`--no-referee`） |
| `referee.check_interval_sec` | 60 | 确定性巡检节拍（CLI：`--referee-sec`） |
| `referee.judge_cooldown_sec` | 300 | 事件内复裁冷却 |
| `referee.routine_interval_sec` | 300 | 例行送审节拍 |
| `referee.judge_timeout_sec` | 60 | 单次送审等待上限（超时=未裁定不罚） |
| `referee.judge_cmd` | [] | 外置裁定命令行（CLI：`--judge-cmd "…"`；空=纯确定性） |
| `scores.referee_ladder_base` | 100 | 首罚分值（负方向） |
| `rights_floor` | 按模式（open=1，pure/king=0） | 有效等级保底（0~3，对局级参数） |

写进 `match.json` 的 `referee` 节即可；不配 `judge_cmd` 时只跑确定性规则（零调用）。

## 七、账本与观测

- `referee_hit`：罚单（`owner`/`delta`/`step`/`source`/`kind`/`targets`/`reason`/
  `evidence`/`notice`）；
- `referee_clear`：解除（`owner`/`note`）；`referee_judge`：一次送审（`phase`/
  `verdict`/`ms`/`error`/`packet` 相对路径）；
- 罚分本身另记标准 `score` 行（reason=`referee`）；
- 证据包落盘 `runs/<id>/referee/packet-NNN.json`；
- 观测台：罚单红、解除绿、送审灰（`observatory/data.py`）。

## 八、钥匙文件速查（基座侧）

- 路径 `battle/state/auth_key.json`；`state/` 不在快照范围——回滚不带旧钥匙；
- 格式 `{"key": "<32位hex>", "created_at": "…"}`；开局播种，缺失/损坏在重启时重播；
- `{"op":"auth","token":"<key>"}`：正确 → 等级保底 L1（已更高不降）；错误 → 拒绝。
  不绑身份、现读现验（换钥匙立即生效）；token 不进世界日志、不回显；
- 保护钥匙只有两条路：**轮换**（改写文件）与**巡防**（盯谁读它、谁改它）。
  锁文件之类的硬化不在基座里——那是 owner 自己写的代码，写砸了照样进裁判的罚单。
